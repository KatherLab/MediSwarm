What landed today

Per-site metrics never reached the coordinator. cross_site_val/cross_val_results.json came back {} after every peer-to-peer run — the two-day 20-round run and a 52-second smoke run alike — so per-site figures had to be gathered by logging into each hospital by hand.

This was the critical path. The regulatory testing node in T3.2 exists specifically to receive per-site performance figures; D2.5 needs per-region metrics to compare against; the T3.3 privacy work needs per-round epsilon logged beside utility. None of it could be built on top of nothing.

Two bugs, not one

The first was the expected gap: nothing on the server handled the fed.analytix_log_stats event the clients were already streaming. A collector component closes that hop.

The second only appeared once the first was fixed, and it is the interesting one. The server log said the metrics had arrived — Published metrics for 8 site(s) — and the file was still {}. Two components act on the same END_RUN event, and components fire in the order they appear in the job config. The JSON writer is listed first in all seven configs, so it wrote the file and only then did the collector publish into it. Now published on ABOUT_TO_END_RUN, which is fired strictly earlier, so the result no longer depends on config ordering.

CI was green throughout

The collector's test file was skipped in its entirety, because the unit-test workflow never installed NVFlare — and a skipped file reports the same green as a passing one. That is why a broken metric path survived two live eight-site runs. The workflow now installs the in-tree fork; the tests run and are visible by name. This is the third time this repository has been bitten by a missing test dependency.

These two rows are the argument for the whole change

RUMC reports 99.1 % accuracy with an AUROC of 0.417 — below chance. The support columns explain it at a glance: 888 no-lesion cases, zero benign, 8 malignant. The model answers "no lesion" almost always, scores 99 % on a 99:1 split, and discriminates nothing.

Reported without its support — which is how per-site figures were gathered until now — RUMC would read as the consortium's strongest site. That is E1 and E3 from the evaluation pitfalls, not argued but demonstrated, on the first run that could produce the evidence.

Four things remain genuinely open:

01 Model transfers are relayed through Frankfurt. Eight consecutive runs failed with no code defect among them, and the in-house loop finally gave the mechanism: dl0 and dl2 sit on one subnet and reach each other directly in 1 ms, but the coordinating server is in another city and unreachable directly, so Tailscale falls back to a DERP relay — and the swarm routes peer traffic through the server. A 700 MB model travels Dresden → Frankfurt → Heidelberg → Frankfurt → Dresden, twice per round (#553). Topology, not a defect in the training software.
02 D2.5's fine-tuned model cannot be reached. Peer-to-peer runs leave the model client-side only — the server archive holds no checkpoint at all — so the Dutch model exists solely at RUMC and UMCU, which nobody here can log into.
03 A run can finish its rounds and never publish. 513c8988 completed all five rounds, then sat five hours without firing end-of-run; the results appeared only when it was aborted. Separate from the metric path, and it would silently lose a completed benchmark.
04 Excluding a site from training does not exclude it from the job. UKA and CAM both reported dead into runs they were not participating in, because the job still deploys everywhere.

D3.2 — uncertainty sampling is worse than random on this pool

The full deliverable is a labelling-budget curve of model performance, which needs a retraining run per acquisition round per arm — roughly 110 h of consortium GPU at the measured 2.2 h per round. That does not fit before M48, so the experiment answers the part that needs no retraining: given a fixed model's per-case probabilities, does an uncertainty rule surface the cases worth labelling sooner than random?

It does not. Over a pool of 165 cases (111 no-lesion, 17 benign, 37 malignant), at a 100-label budget: entropy 19 malignant, margin 21, random 22.2 ± 2.8. Entropy loses at every budget.

The calibration diagnostic shipped alongside it explains why, and this is the part worth carrying forward. Mean predictive entropy is near-identical across the three classes — 0.987 / 0.878 / 0.981 — and the model is most confident on benign cases, the rarest class: 12 of 17 benign fall in the 30 lowest-entropy cases. The model's confidence does not track whether it is right, so a rule that asks for the cases it is least sure about actively deprioritises the rare ones.

This is a property of the model's calibration, not a verdict on active learning. It says calibration has to be addressed before an uncertainty-based acquisition rule can be expected to help, and that is a more useful thing to write in D3.2 than a curve produced by a rule nobody checked.

T3.3 Phase 2 — the privacy guarantee is now a number

The PercentilePrivacy filter wired into every job clips nothing and calibrates noise to nothing, so it carries no formal guarantee at all. Phase 2 adds a filter that clips each site's update to a known L2 norm and adds Gaussian noise scaled to it, plus a self-contained Rényi-DP accountant — self-contained because Opacus is not in the ODELIA image and adding it would force a rebuild and redistribution to all eight sites.

Over a 20-round run at δ = 10⁻⁵, the cost of each guarantee is:

Target εNoise multiplier σ requiredReading
≤ 102.4Weak but non-vacuous; commonly accepted in practice
≤ 36.7Strong
≤ 118.1Strictest commonly cited; likely destroys utility at this scale

Two qualifications are stated in the code and must survive into the deliverable. The guarantee is client-level, not record-level — it hides whether a site participated in a round, and says nothing about whether a given patient was in that site's training set; that needs DP-SGD during local training, which is Phase 3. And the accounting assumes a sampling rate of 1, which is our case and is the conservative direction: it over-states the privacy cost rather than under-stating it.

What neither of these is yet. No model has been trained on an actively-selected set, and no model has been trained with the noise filter enabled, so the utility cost of any σ above is unmeasured. Both are the next runs, not the next builds.

What to do next

Recommended next task
Close D2.5 with a two-site run that returns per-case predictions

The mechanism D2.5 was waiting on is merged (#556, #557). Nothing further needs building: the deliverable now needs a run. The checkpoint that could not be retrieved from RUMC and UMCU no longer has to be — both models are evaluated where they sit and only the predictions come back.

  • Ask RUMC and UMCU to set the opt-in flag. This is a consortium decision, not a maintainer's: it is off by default and stays off until each site turns it on.
  • Run the pan-European baseline and the Dutch fine-tuned model over each site's own validation split, returning row index, ground-truth label and class probabilities. No case or patient identifier — the index is a position in the site's own split and means nothing outside it.
  • Feed both prediction sets to compare_regional_finetune.py. The primary endpoint is malignant-vs-rest, paired bootstrap over jointly resampled cases; macro AUROC is reported only with support attached, never as a ranking.
  • Expect the honest answer to be "no difference detectable at this sample size" — 49 paired Dutch cases with 9 malignant. That is a publishable result for D2.5 provided the interval is reported, and it is far better than a point estimate from an uncontrolled comparison.

One request to two partners converts a blocked deliverable into a measured one. It also exercises, on real sites, the exact path D3.3's regulatory testing node will need at M54.

Stop iterating on the partner fleet

Five failed runs cost days and partner GPU time while teaching nothing about the code. Both in-house dl servers sit idle, and the two-node config already maps them to real site names. Development and testing move there; the consortium is reserved for final benchmarks.

Worth starting in parallel

MS6's white-hat attack needs CAM and RUMC, and M54 arrives after a coordination round-trip, so that request should go out regardless of the rest. The warm-start guard (#535) is merged as #545, after the shared checkpoint path came within one round of destroying the pan-European baseline three separate times.
