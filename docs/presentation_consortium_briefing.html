The problem

Until this week, results never left the hospitals

The coordinator's results file came back empty after every peer-to-peer run — after a two-day twenty-round run and after a fifty-second test run alike.

What that cost us

  • Per-site figures had to be collected by logging into each hospital by hand
  • No central view of how the shared model performs at each centre
  • Blocked the regulatory testing node, the regional comparison, and privacy accounting

Why it went unnoticed

  • Every run reported success
  • The server log said metrics had arrived from all eight sites
  • Automated tests passed — while silently skipping the file that would have caught it

Read the highlighted row carefully. 99.1 % accuracy with an AUROC of 0.417 — below chance. Of 896 cases, 888 carry no lesion and none are benign. A model that answers "no lesion" almost always scores 99 % and discriminates nothing.

These are validation figures shown as evidence that the mechanism works — not model performance results.

4
Why this matters clinically

A number without its denominator is not a result

Reported on its own, Radboud's 99 % would make it look like the strongest centre in the consortium. It is an artefact of a 99:1 class split.

We have already been caught by this

UMC Utrecht was described as performing materially worse than other centres. That came from a macro-averaged AUROC in which one class was represented by two cases. Excluding that class, Utrecht moves 0.602 → 0.717 and Cambridge 0.710 → 0.908.

What we do now

  • Every metric travels with its per-class support count
  • Ranking centres by macro AUROC is off the table where a class has single-digit support
  • The failure modes are written up for all partners
Nothing here reflects on any centre's data quality. It reflects on how we were summarising it.

The software is fixed. The fleet is the bottleneck.

Eight consecutive runs, no code defect among them. Development has moved to in-house servers so the consortium fleet is used only for final benchmark runs.

We now know why the in-house runs failed too. Model transfers were being relayed through Frankfurt: our two test machines sit on one subnet and talk in 1 ms, but the coordinating server is in another city, and the swarm routes every transfer through it. A 700 MB model was crossing the country twice per round. That is a network topology problem, not a defect in the training software.

7
The ask

Let sites return per-case predictions, not just summaries

What we would send back
A row number, the ground-truth label, and the model's class probabilities. No case identifier and no patient identifier — the row number is a position within your own validation split and means nothing outside it. No images. Nothing new is computed; this is what your site already writes to its own disk during a normal training run.

Why we need it

  • Regional fine-tuning (D2.5) is currently blocked on moving a 722 MB model out of two hospitals — this removes that need entirely
  • Proper statistical comparison needs case-level pairing; summaries cannot provide it
  • The regulatory testing node due at M54 requires it regardless

What we need from you

  • Confirmation that this is acceptable under your local data agreement
  • It stays off unless your site switches it on — the decision is yours, per site
  • Nothing technical — no new kit, no reconfiguration
  • Please keep clients online for the active-learning tests
