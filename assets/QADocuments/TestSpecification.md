## 1 Introduction and Overview

This document summarizes the test design specification for MediSwarm tests.

Some of the software requirements refer to application code. MediSwarm contains an example productive ApC used in the corresponding tests. MediSwarm is meant to be used for other future ApCs that (obviously) cannot be tested here. The existing tests can serve as a blueprint for implementing tests for future productive ApCs. However, the existing tests do not check whether trained models solve the intended machine learning task or with which performance. Such tests are needed in addition for future productive ApCs.

### 1.1 Environment

#### 1.1.1 Hardware Environment

The test hardware consists of a VM with an Intel(R) Xeon(R) Gold 5320 CPU @ 2.20GHz (12 cores), 167 GB RAM, and an NVIDIA A100 GPU (80GB GPU RAM).

#### 1.1.2 Software Environment

The software environment uses an Ubuntu 24.04.4 LTS operating system.
A clone of the MediSwarm repository, and a MediSwarm Docker image for the corresponding code version is required to run the tests. The tests are orchestrated via the bash script runIntegrationTests.sh. The following software is required:

* Docker
* git
* bash
* GNU coreutils
* curl
* expect
* grep
* tar
* unzip

### 1.2 Test Data

No dataset is required to run the tests. Some test steps require a test dataset (image data and csv lists with metadata). For this purpose, synthetic datasets with the required properties are generated by utility scripts as part of the respective tests.

### 1.3 Scope

#### 1.3.1 Test Swarm Setup

For testing swarm capabilities, a swarm consisting of a server node, admin node, and two client nodes is run on the same host.

#### 1.3.2 Aspects not Covered

##### 1.3.2.1 Cybersecurity

Cybersecurity requirements not covered by the tests described here, a separate analysis will be needed.

##### 1.3.2.2 Load Testing

Training jobs during the test use a small, synthetic dataset; swarms with a realistic number of nodes and realistic dataset sizes are not covered by the tests.

##### 1.3.2.3 Stress Testing

Effects of simultaneously running jobs within a single swarm, concurrent swarms on the same hosts, and high memory/CPU/GPU/disk IO loads due to other usage of the hosts are not covered by the tests.

##### 1.3.2.4 Network/VPN Latency

With all test nodes running on the same host, effects of limited network bandwidth, latency, or interruptions are not covered by the tests.

##### 1.3.2.5 Algorithm Validation

MediSwarm does not provide application code or data for productive model training. Hence, no validatable results beyond the integration tests can be generated as part of MediSwarm.

#### 1.3.3 Requirements Applying to Execution Environment

The following requirements apply to the execution environment and need to be verified by maintainers of the hosts running MediSwarm nodes: K.1, K.10, K.11, K.12, K.13, K.14, K.15, K.16, L.7. These requirements are not covered by the MediSwarm tests.

#### 1.3.4 Requirements to be Handled Outside the System

The following requirements need to be addressed by organizational means outside the system: A.4, A.12, A.13, B.1, B.14, C.12, E.11, G.7, N.6. The requirements are not covered by the MediSwarm tests.

#### 1.3.5 Requirements Applying to Future Application Code

The following requirements apply to future application code outside the system and need to be verified by code review: A.2, B.5, B.10, B.13, E.3, F.5, F.6, F.7, F.8, G.2, G.4, G.5, G.6, G.8, H.1, H.2, H.3, H.4, M.2.

#### 1.3.6 System Requirements not Tested

For part of the software requirements, it is not feasible to test them as part of the test suite because triggering specific errors would require modification to code or parameters (e.g., timeouts), making the tested code different from the production code: A.7 (number of responsive client nodes \< total number of client nodes), A.8 (training continues if nodes drop out), D.21 (aggregation if fewer than all nodes have provided results).

## 2 Unit Test Design

There are no unit tests implemented for MediSwarm, but access to NVFlare unit tests is provided.

### 2.1 Unit Tests

#### 2.1.1 run\_nvflare\_unit\_tests

This test installs additional python packages in the container. The test needs to be run on a non-sliced GPU (MIG disabled). The test reports a line coverage at the end, output prior to that needs to be inspected manually for issues.
Note that NVFlare also provides integration tests. These are not called as part of the NVFlare test suite as all functionality necessary for MediSwarm covering software requirements are tested by MediSwarm integration tests and executing NVFlare integration tests in the MediSwarm container environment (for which those tests were not designed) leads to spurious errors.

**Expected result:** test reports no issues

**Requirements covered:** A.10 (by NVFlare/tests/unit\_test/app\_common/aggregators/in\_time\_accumulate\_weighted\_aggregator\_test.py)

## 3 Integration Test Design

Integration tests were implemented to test whether the MediSwarm Software requirements are met by the implementation, i.e., largely complete functional coverage is achieved.
Of the 141 requirements specified in MediSwarm-SPEC-SRS, 97 are covered by the tests, 11 are covered partially by the tests, 9 are to be verified (also) by code review, and 37 are requirements to be met (also) outside the system.

### 3.1 Integration Tests

#### 3.1.1 check\_files\_on\_github

Retrieve files from the public repository on github.com and check for expected keywords in expected files to verify that

* the source code is available on github
* has the expected MIT license
* has README files with instructions for swarm participants, developers, and swarm operators
* the ApC for the Docker/GPU preflight check is python code

Note: This test is currently disabled as the repository is temporarily private.

**Expected result:** automatic checks pass

**Requirements covered:** G.1, G.3, K.3, M.1, M.2, M.3, N.1, N.2, N.3, N.4, N.5.

#### 3.1.2 run\_dummy\_training\_standalone

Run the minimal training in the MediSwarm Docker container without GPU, check for expected output (error) to verify that

* the minimal training fails if no GPU is available

Run the minimal training in the MediSwarm Docker container with GPU, check for expected output (success) to verify that

* the minimal training run completes without error.

**Expected result:** automatic checks pass

**Requirement covered:** E.9

#### 3.1.3 run\_dummy\_training\_simulation\_mode

Run the minimal training in the MediSwarm Docker container in NVFlare swarm simulation mode.

* A manual check of the output is needed to verify that this has completed successfully as errors may not be propagated.

**Expected result:** passes and test output does not report issues

**Requirements covered:** A.9, A.10, A.11, D.2, D.7, D.8, D.9, D.10, D.11, D.12, D.13, D.14, D.15, D.16, D.17, D.18, D.19, D.20, D.21, D.23, D.24, D.25.

#### 3.1.4 run\_dummy\_training\_poc\_mode

Run the minimal training in the MediSwarm Docker container in NVFlare swarm proof-of-concept mode.

* A manual check of the output is needed to verify that this has completed successfully as errors may not be propagated.

**Expected result:** passes and test output does not report issues

**Requirements covered:** D.3, D.7, D.8, D.9, D.10, D.11, D.12, D.13, D.14, D.15, D.16, D.17, D.18, D.19, D.20, D.21, D.23, D.24, D.25.

Run the example productive ApC in the MediSwarm Docker container in NVFlare swarm simulation mode.

**Requirements covered:** D.2, D.7, D.8, D.9, D.10, D.11, D.12, D.13, D.14, D.15, D.16, D.17, D.18, D.19, D.20, D.21, D.23, D.24, D.25.

#### 3.1.6 create\_startup\_kits\_and\_check\_contained\_files

Build startup kits and verify that expected files are contained in the respective folders and archives to verify that

* startup kits are built successfully
* docker script has options for preflight checks, local training, starting swarm client, and listing licenses.
* certificate files are contained in startup kit folder
* certificates and docker script are contained in startup kit archive

**Expected result:** automatic checks pass

**Requirements covered:** B.11, B.12, C.1, C.2, C.11, L.6.

#### 3.1.7 run\_list\_licenses

Run docker scripts from startup kits for admin, server, and client nodes with the option to list installed packages; check for expected output to verify that

* startup kits have this option
* a sample of expected packages is contained in the listings
* expected licenses are contained in the listings
* pre-trained model weights are mentioned in the listings

**Expected result:** automatic checks pass

**Requirement covered:** C.13.

#### 3.1.8 run\_docker\_gpu\_preflight\_check

Run the Docker/GPU preflight check via the client startup kit with timeout and check for expected output to verify that

* the startup kit provides this option
* the Docker/GPU preflight check succeeds
* it does so within one minute

Notes

* We do not test what happens if Docker is not installed or not working. This cannot fail silently in productive use: Any usage without Docker installed will fail as soon as Docker is used.
* We do not test what happens if no or an incorrect GPU is provided. This cannot fail silently in productive use: The startup kits’ docker.sh scripts prompt for the GPU if not specified via a command line argument, docker run fails if an invalid GPU is specified.

**Expected result:** automatic checks pass

**Requirements covered:** C.1, C.2, C.8, E.5, E.8, E.10.

#### 3.1.9 run\_data\_access\_preflight\_check

Run the data access preflight check (using the example productive ApC) with timeout via the client startup kit, check for expected output to verify that

* the startup kit provides this option
* the expected numbers of training, validation, and test images are reported
* one successful training epoch has finished within one minute
* expected warnings and errors about implausibilities in the loaded dataset are printed
* uids involved in implausibilities are printed only if run with the respective option
* the preflight check fails if no data can be loaded

The test contains of three steps: run\_data\_access\_preflight\_check, run\_data\_access\_preflight\_check\_log\_details, and run\_data\_access\_preflight\_check\_without\_data.

**Expected result:** automatic checks pass

**Requirements covered:** B.8, B.9, B.13, B.14, C.1, C.2, C.9, E.4, E.5, F.1, F.2, F.3, F.4, J.6.

#### 3.1.10 verify\_wrong\_certificates\_are\_rejected

Replace certificate files in startup kits by certificates from a different swarm instance and verify that connections to nodes from the current instance are rejected, in order to verify that

* a swarm server rejects swarm client nodes and admin nodes with incorrect certificates
* a swarm client does not connect to a server with incorrect certificate
* an admin node does not connect to a server with incorrect certificate

**Expected result:** automatic checks pass

**Requirements covered:** C.1, L.3, L.4, L.5, L.6.

#### 3.1.11 run\_dummy\_training\_in\_swarm

Start a server node, start two client nodes, start an admin node, deploy a minimal training via the admin console, wait for the training to finish, check that client and server logs contain expected messages and that expected client files are stored on the host file system, to verify that

* swarm server, clients, and admin node can be started via startup kit
* admin console can submit ApC for swarm preflight check
* server log contains expected output (clients connected, job started, clients report when round done and training done)
* client log contains expected output (connects to server, receives training task, sends round result to aggregator)
* client stores received application code
* client stores best and last global model checkpoint
* model checkpoints are at most 1 MiB

**Expected result:** automatic checks pass

**Requirements covered:** A.1, A.3, A.5, A.6, B.3, B.4, B.6, B.7, B.13, B.14, C.1, C.2, C.4, C.6, C.10, D.1, D.4, D.5, D.6, D.7, D.8, D.9, D.10, D.11, D.12, D.13, D.14, D.15, D.16, D.17, D.18, D.19, D.20, D.21, D.22, D.23, D.24, D.25, E.1, E.2, E.5, E.6, E.7, E.12, E.13, E.14, E.15, E.16, J.1, J.2, J.3, J.4, J.5, J.7, J.8, K.6, K.7, K.8, L.1, L.2, L.6.

#### 3.1.12 run\_container\_with\_pulling

As preparation, start\_registry\_docker\_and\_push is executed. This tarts a custom docker registry (also as a Docker container) on the test host, builds a MediSwarm Docker image, pushes it to the local registry to verify that pushing the image works. This takes several minutes despite not requiring transmission via the network. The output needs to be inspected manually for issues.
After deleting the image on the host, the docker.sh script from a startup kit to verify that the required image is pulled automatically.

**Expected result:** passes and test output does not report issues

**Requirements covered:** C.3, C.5, C.7, K.4, K.5.

#### 3.1.13 run\_3dcnn\_local\_training

Run a local training using the example productive ApC via a client startup kit to verify that the startup kit provides this functionality and that this ApC can be used for local training. This test has a timeout of one hour and checks for expected output about successfully completed training.

**Expected result:** automatic checks pass

**Requirements covered:** B.10, B.13, B.14, C.1, C.11, E.2, E.5, F.5, F.6, F.7, F.8.

#### 3.1.14 run\_3dcnn\_training\_in\_swarm

Start a server node, start two client nodes, start an admin node, deploy a minimal training via the admin console, wait for the training to finish, check that client and server logs contain expected messages and that expected client files are stored on the host file system. This test is similar to the run\_dummy\_training\_in\_swarm test, but uses the example productive ApC and contains fewer checks for expected output. The test times out after one hour.

**Expected result:** automatic checks pass

**Requirements covered:** A.1, A.3, A.6, B.3, B.4, B.5, B.6, B.13, B.14, C.1, C.2, C.4, C.6, D.1, D.4, D.5, D.6, D.7, D.8, D.9, D.10, D.11, D.12, D.13, D.14, D.15, D.16, D.17, D.18, D.19, D.20, D.21, D.22, D.23, D.24, D.25, E.1, E.2, E.5, F.5, F.6, F.7, F.8, J.3, K.6, K.7, K.8, L.1, L.2, L.6.
